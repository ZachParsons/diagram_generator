# Diagram Generator

A p5.js-based generator for randomized node/relationship diagrams, with a
live parameter panel and a data model designed to be portable: the
generator's output is a plain JSON object that can be fed into a
different visualizer, and (eventually) real input data can be fed into
the generator in place of pure randomness.

No build step: p5.js and Tweakpane load from CDNs, everything else is
plain scripts. Just open `index.html` in a browser.

```
open index.html
```

(If your browser blocks something for file:// pages, serve it instead:
`python3 -m http.server 8000` from this directory, then visit
`http://localhost:8000`.)

In the canvas you can drag things directly: a node moves by dragging its
shape; an edge bends by dragging anywhere along its path (this sets
`controlPoint`, see below); and a floating (non-node) edge endpoint --
`source`/`target`/an `extraSources`/`extraTargets` entry that's a literal
point rather than a node id -- can be dragged to reposition it directly.
All of this is in-memory only and resets on the next Regenerate.

The table (nodes/edges as plain HTML tables, see `tableRenderer.js`) isn't
a separate screen -- it's a drawer that slides up over the bottom of the
canvas, toggled by the "Table" handle at the bottom of the main view, so
you can have both visible at once. It stays up to date continuously, so
expanding it never shows stale data.

## Architecture

```
src/rng.js             seeded PRNG (mulberry32 + xmur3 string hashing)
src/schema.js           the diagram JSON schema + default params
src/layouts.js          grid / random / circular node placement
src/generator.js        params (+ optional input data) -> diagram JSON
src/canvasRenderer.js   diagram JSON -> p5 canvas drawing
src/tableRenderer.js    diagram JSON -> HTML table (2nd, independent visualizer)
src/controls.js         Tweakpane panel bound to the params object
src/main.js             wires it all together, handles import/export
data/sample-input.js    example "given input data" dataset
```

Everything hangs off a single global namespace object, `DG`, populated by
each script (no bundler, so no ES modules/CORS issues when opened via
`file://`).

The key design decision is the boundary between **generator** and
**renderer**: renderers only ever see a diagram JSON object and know
nothing about params, randomness, or how the diagram was produced. That's
what makes the output pluggable -- `canvasRenderer.js` and
`tableRenderer.js` are two interchangeable consumers of the same schema,
and a diagram exported from this tool (or built by hand, or produced by
some other generator) can be loaded straight into either one via
"Import diagram JSON".

## The diagram schema

```jsonc
{
  "meta": {
    "seed": "abc123",
    "width": 900,
    "height": 600,
    "background": "#101418",
    "generatedAt": "2026-01-01T00:00:00.000Z",
    "generatorVersion": "0.1.0"
  },
  "nodes": [
    {
      "id": "n0",
      "label": "N0",
      "group": null,
      "shape": "oval",              // oval | triangle | quad | blob (a label -- see below)
      "x": 120, "y": 80,            // center
      "w": 60, "h": 40,             // nominal bounding box used to derive `points`
      "points": [{ "x": -28, "y": -14 }, "..."],  // closed outline, local coords, pre-rotation
      "curved": true,                // true: smooth curve through points; false: straight edges
      "rotation": 0.4,               // radians
      "fill": "hsla(210, 65%, 55%, 0.8)",  // fill only -- shapes have no outline
      "fillOpacity": 0.8
    }
  ],
  "edges": [
    {
      "id": "e0",
      "source": "n0",                  // a node id, OR a literal {"x":.., "y":..} floating point
      "target": "n1",
      "extraSources": [],               // optional: other refs that converge into `source`
      "extraTargets": ["n2", { "x": 400, "y": 120 }],  // optional: `target` splits into these too
      "style": "curved",                // straight | curved | orthogonal (path shape)
      "pattern": "dashed",              // solid | dashed | dotted | striped (stroke texture)
      "widthStart": 1.5, "widthEnd": 4,     // taper -- can differ
      "opacityStart": 0.4, "opacityEnd": 0.9,  // fade -- can differ
      "color": "hsl(40, 15%, 70%)",
      "color2": "hsl(200, 15%, 70%)",   // alternate color, used by the 'striped' pattern
      "arrowStart": false, "arrowEnd": true,
      "sourceGap": -3, "targetGap": 6,  // extra px pulled back from a node boundary (negative = overshoot)
      "label": null
    }
  ]
}
```

Colors are plain CSS color strings, positions/sizes are plain numbers --
the schema has no dependency on p5 or any particular renderer.

### Shapes are always irregular, on purpose

There are deliberately no circles, equilateral triangles, squares, or
regular polygons anywhere in this generator. Every node is built from a
`points` array generated by pushing each vertex of an evenly-spaced
ellipse/polygon off its base angle and base radius by a random amount
(`generator.js`'s `irregularPoints`/`shapeGeometry`), with a jitter floor
so a shape can never collapse back into something perfectly symmetric --
the `irregularity` param only makes the effect stronger, it can't turn it
off. The four shape families just tune how many vertices and how much
jitter:

- **oval**: 7 vertices, low jitter, smooth curve -> lopsided ovals/eggs, never a true ellipse.
- **triangle**: 3 vertices, high jitter, straight edges -> scalene triangles.
- **quad**: 4 vertices, high jitter, straight edges -> rhombus/trapezoid/kite-like irregular quadrilaterals.
- **blob**: 6-11 (configurable) vertices, highest jitter, smooth curve -> organic asymmetric blobs.

Renderers don't know any of this -- `canvasRenderer.js` only looks at
`points` and `curved` and draws a closed straight path or a closed
Catmull-Rom curve. Anything that fills in `points`/`curved` in the schema
renders correctly, including a shape family this generator doesn't have.

### Edges are more than a colored line

Every edge is a *trunk* (`source` -> `target`) that's independently tapered
(`widthStart`/`widthEnd`), faded (`opacityStart`/`opacityEnd`), and drawn
in one of four textures:

- **solid**: a continuous tapered ribbon.
- **dashed**: the ribbon with gaps cut out along its length.
- **dotted**: a row of small circles instead of a ribbon, sized by the local taper width.
- **striped**: a continuous ribbon that alternates between `color` and `color2` every so often, like a barber pole.

Edge color comes from its own `edgeHueMin`/`edgeHueMax`/`edgeSaturationMin`/
`edgeSaturationMax`/`edgeLightnessMin`/`edgeLightnessMax` params -- deliberately
separate from the node color params, so edges get just as much random hue/
saturation/lightness variety as nodes do without literally sharing a palette
with them.

An edge endpoint (`source`/`target`, and any `extraSources`/`extraTargets`)
is either a node id, resolved to that node's center and pulled back to its
boundary (+`sourceGap`/`targetGap`, which can be negative to overshoot into
the node), or a literal `{x, y}` point that isn't attached to anything --
this is what makes an edge that doesn't start or end at a node. `sourceGap`/
`targetGap` are randomized per edge by default so lines don't all crisply
hug the exact same offset from every node.

`extraSources`/`extraTargets` add thin branch lines that converge into the
trunk's start or fan out from its end -- one edge can represent several
nodes converging into a shared path, or one path splitting toward several
targets. `canvasRenderer.js` renders all of this generically: it samples
whatever path shape (`style`) the edge specifies into points, interpolates
width/opacity along those samples, and only branches into pattern-specific
logic for how much of the ribbon at each point is actually drawn (dash gaps,
stripe color, or dots-instead-of-ribbon) -- see `drawTrunk` in
`canvasRenderer.js`.

### Size tiers

With `sizeTiers` on (the default), node size and edge width don't sample
evenly across `sizeMin`-`sizeMax` / `edgeWidthMin`-`edgeWidthMax` -- each
roll instead lands in either the bottom 40% or top 40% of that range
(`largeTierProbability` sets the odds of landing in the top), skipping the
middle entirely. That's what produces a visible mix of small and large
nodes/edges rather than a smooth gradient of in-between sizes. See
`pickSizeTier`/`tieredRange` in `generator.js`. Node width and height share
one tier roll (so a node reads as clearly "small" or "large" overall,
even though its exact width/height still vary within that tier); an edge's
two ends each roll their own tier, so some edges taper dramatically from a
large end to a small one.

## Generating from input data

`DG.generateFromData(inputData, params)` takes:

```jsonc
{
  "nodes": [
    { "id": "api", "label": "API Gateway", "group": "backend", "connections": ["auth", "orders"] }
  ]
}
```

and produces a full diagram: node identity, labels, grouping, and the
edge graph come from your data; position (layout) and visual style
(shape pool, size range, color range, etc.) still come from the
same randomization params as pure-random generation, so the same style
controls apply whether or not you're driving it from real data. Nodes
sharing a `group` get a consistent (but still randomized) hue.

Try it in the app: check "Use input data instead of pure random" in the
sidebar, then click "Load sample data" (see `data/sample-input.js`), or
import/paste your own `{ nodes: [...] }` JSON.

## Extending

- **New shape type**: add its name to `DG.SHAPES` in `schema.js` and a
  vertex-count/jitter/`curved` entry to `SHAPE_FAMILY` in `generator.js`
  -- rendering (`canvasRenderer.js`) needs no changes since it only
  reads `points`/`curved`.
- **New layout**: add a function to `LAYOUT_FNS` in `layouts.js` and to
  the `layout` dropdown options in `controls.js`.
- **New visualizer**: write a function `(diagram) => void` that only
  reads the schema above -- see `tableRenderer.js` for the minimal
  example -- and give it a spot in `index.html`/`main.js` (as its own
  drawer, alongside the table, or however it should coexist with the
  canvas).
- **New relationship types**: containment/alignment/grouping (rather than
  a line between two points) could be added as a parallel array in the
  schema (e.g. `diagram.groups`) without touching the node/edge contract.
- **New edge texture**: add its name to `DG.EDGE_PATTERNS` in `schema.js`
  and a branch in `drawTrunk`'s pattern handling in `canvasRenderer.js`
  (which segment(s) to skip, or what to draw instead of a plain ribbon
  segment, at each sampled point along the path).

Note: `generateFromData()` deliberately does not add floating edges or
split/converge branches -- those are decorative randomization, and a
diagram built from real data should only show relationships that are
actually in that data.

## Known simplifications (v0)

- Edge routing is naive: straight/curved/orthogonal connect node
  centers, pulled back to approximate node radius; it doesn't route
  around other nodes.
- "Random" edge mode is O(n^2) over node pairs -- fine up to a few
  hundred nodes, not built for huge graphs.
- No persistence/undo beyond seeded regeneration and JSON export/import.
